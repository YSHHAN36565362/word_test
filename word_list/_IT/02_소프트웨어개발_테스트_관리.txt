REST
HTTP URI로 자원을 표시하고 HTTP Method로 해당 자원에 대한 CRUD 연산을 적용하는 방식
[구성] URI(자원 표현) + HTTP Method(행위) + 표현(JSON 등)
[의미] 자원을 URI로 구분하고 HTTP 메서드로 행위를 표현하는 웹 아키텍처 스타일
[구분] CRUD와 HTTP Method 대응
· CREATE: POST (자원 생성)
· READ: GET (자원 정보 조회)
· UPDATE: PUT (자원 정보 업데이트)
· DELETE: DELETE (자원 삭제)
[치트키] "생성은 포스트(POST), 조회는 게시판 조회 GET, 수정은 PUT, 삭제는 DELETE"
[예문] REST 방식에서는 GET으로 자원을 조회하고 DELETE로 자원을 삭제한다

소프트웨어 테스트의 원리
소프트웨어 테스트에서 지켜야 할 7가지 원리 (암기: 결완초집살정오)
[구성] 결함 존재 + 완벽 불가 + 초기 시작 + 결함 집중 + 살충제 패러독스 + 정황 의존 + 오류 부재의 궤변
[의미] 테스트의 한계와 효율적인 수행 방법을 정리한 일반 원리
[구분] 원리별 의미
· 결함 존재 증명: 결함이 존재함을 밝힐 뿐 결함이 없다는 것을 증명할 수 없음
· 완벽 불가: 완벽한 테스팅은 불가능하며 시도 자체가 시간과 자원의 낭비
· 초기 시작: 개발 초기에 테스트를 시작해야 후반 비용 증가를 막을 수 있음
· 결함 집중: 오류의 80%는 전체 모듈의 20%에서 발견 (파레토 법칙과 유사)
· 살충제 패러독스: 동일한 테스트 케이스를 반복하면 새로운 버그를 찾지 못함
· 정황 의존: 소프트웨어 성격에 맞게 테스트
· 오류 부재의 궤변: 요구사항을 충족하지 못하면 결함이 없어도 품질이 높다고 볼 수 없음
[치트키] "결(결함존재) 완(완벽불가) 초(초기) 집(집중) 살(살충제) 정(정황) 오(오류부재) = 결완초집살정오"
[예문] 동일한 테스트 케이스를 반복하면 새로운 버그를 찾지 못하는 현상은 살충제 패러독스이다

WSDL
XML으로 작성되며 웹 서비스와 데이터를 주고받기 위한 설명서
[구성] XML 기반 + 서비스 설명 + 이용 방법 명세
[의미] 웹 서비스의 위치와 호출 방법을 기술한 문서
[치트키] "WSDL = 웹 서비스 설명서(Description)"
[예문] 웹 서비스의 인터페이스를 XML로 기술한 설명서는 WSDL이다
[헷갈리는 단어] UDDI - WSDL은 설명서, UDDI는 그 설명서를 등록·검색하는 저장소

UDDI
웹 서비스 정보인 WSDL을 등록하고 검색하기 위한, 공개적으로 접근·검색 가능한 레지스트리
[구성] 등록 + 검색 + 공개 레지스트리
[의미] 서비스 제공자와 이용자를 연결하는 웹 서비스의 저장소
[치트키] "UDDI = 서비스 전화번호부(Directory)"
[예문] WSDL을 등록하고 검색하는 레지스트리는 UDDI이다
[헷갈리는 단어] WSDL - UDDI는 저장소(검색), WSDL은 설명서

SOAP
XML 기반의 메시지를 컴퓨터 네트워크 상에서 교환하는 프로토콜
[구성] XML 메시지 + 네트워크 전송 프로토콜
[의미] 웹 서비스 간에 구조화된 정보를 주고받기 위한 메시징 규약
[치트키] "SOAP = 비누로 깨끗이 포장한 XML 메시지"
[예문] 웹 서비스에서 XML 메시지를 교환하는 프로토콜은 SOAP이다

DRS(재해복구시스템)의 유형
재해 시 업무를 신속히 복구하기 위한 재해복구센터의 운영 방식 4가지
[구성] Mirror Site → Hot Site → Warm Site → Cold Site
[의미] 복구 속도가 빠를수록 비용이 높고, 느릴수록 비용이 낮아지는 구조
[구분] 유형별 특징 (복구 소요 시간 RTO 기준)
· Mirror Site: 주 센터와 복구센터가 모두 운영 상태, RTO는 즉시
· Hot Site: 주 센터와 동일한 자원을 대기 상태로 원격지에 보유하며 미러링으로 최신 상태 유지, RTO는 4시간 이내
· Warm Site: 중요성이 높은 자원만 부분적으로 보유, 백업 주기는 수 시간~1일, RTO는 수일~수주
· Cold Site: 데이터만 원격지에 보관하고 재해 시 필요 자원을 조달해 복구, RTO는 수주~수개월
[치트키] "미러(즉시) → 핫(4시간) → 웜(수일) → 콜드(수개월), 뜨거울수록 빠르고 차가울수록 늦다"
[예문] 데이터만 원격지에 보관하고 재해 발생 시 자원을 조달해 복구하는 센터는 Cold Site이다

RTO(Recovery Time Objective)
재해 복구 목표 시간
[구성] 재해 발생 → 서비스 중단 → RTO 이내 복구
[의미] 재해로 서비스가 중단되었을 때 복구하는 데 걸리는 최대 허용 시간이며 0이면 실시간 복구를 의미
[치트키] "T(Time) = 시간, 얼마나 걸려서 되살릴 것인가"
[예문] 재해 발생 후 서비스를 복구하는 데 허용되는 최대 시간은 RTO이다
[헷갈리는 단어] RPO - RTO는 복구 시간, RPO는 허용 가능한 데이터 손실 시점

RPO(Recovery Point Objective)
재해 복구 목표 시점
[구성] 재해 발생 시점 ← 마지막 백업 시점 (이 간격이 RPO)
[의미] 재해 발생 시 데이터 손실을 수용할 수 있는 손실 허용 시점이며 데이터 손실 최소화와 관련된 개념
[치트키] "P(Point) = 시점, 어느 시점의 데이터까지 살릴 것인가"
[예문] 재해 시 어느 시점까지의 데이터 손실을 허용할지 정한 지표는 RPO이다
[헷갈리는 단어] RTO - RPO는 데이터 손실 시점, RTO는 복구 소요 시간

EAI
미들웨어(Hub)를 이용해 비즈니스 로직을 중심으로 기업 내 애플리케이션을 통합 연계 (암기: 포허메하)
[구성] Point-to-point + Hub&Spoke + Message Bus + Hybrid
[의미] 서로 다른 애플리케이션을 하나의 시스템처럼 연동하기 위한 통합 솔루션
[구분] 방식별 특징
· Point-to-point: 가장 기초적인 1:1 통합 방법
· Hub&Spoke: 어플리케이션 사이에 허브 미들웨어를 두어 데이터를 중앙 집중식으로 전송
· Message Bus: 애플리케이션 사이에 버스 미들웨어를 두어 처리 (주로 ESB)
· Hybrid: Hub&Spoke와 Message Bus의 혼합형
[치트키] "포(점대점) 허(허브) 메(메시지버스) 하(하이브리드) = 포허메하"
[예문] 허브 시스템을 통해 데이터를 중앙 집중식으로 전송하는 EAI 방식은 Hub&Spoke이다
[헷갈리는 단어] ESB - EAI는 점대점·허브 중심의 중앙 집중, ESB는 버스형·SOA 중심

ESB
미들웨어(Bus)를 이용해 서비스 중심으로 관련 시스템을 유기적으로 연계하는 방식
[구성] 버스 미들웨어 + 서비스 중심 + SOA + 느슨한 결합
[의미] 서비스 단위로 시스템을 연결해 유연성과 재사용성을 높임
[구분] EAI와 ESB 차이
· ESB: SOA, 느슨한 결합, 버스형
· EAI: 점대점, 허브&스포크, 중앙 집중
[치트키] "ESB = 서비스(S) 버스(B), 버스를 타고 느슨하게 연결"
[예문] 버스 형태의 미들웨어로 서비스를 느슨하게 결합하는 방식은 ESB이다
[헷갈리는 단어] EAI - ESB는 버스형, EAI는 허브형

애플리케이션 성능 측정 지표
애플리케이션의 성능을 평가하는 4가지 지표 (암기: 처응경자)
[구성] 처리량 + 응답시간 + 경과시간 + 자원 사용률
[의미] 처리 능력과 속도, 자원 소비를 종합적으로 측정
[구분] 지표별 의미
· 처리량(Throughput): 주어진 시간에 처리할 수 있는 트랜잭션 수
· 응답시간(Response Time): 입력이 끝난 후 응답 출력이 시작될 때까지의 시간
· 경과시간(Turnaround Time): 트랜잭션 처리 후 결과 출력이 완료될 때까지 걸리는 시간
· 자원 사용률(Resource Usage): 트랜잭션 처리 동안 CPU, 메모리, 네트워크 사용량
[치트키] "처(처리량) 응(응답시간) 경(경과시간) 자(자원사용률) = 처응경자"
[예문] 입력이 끝난 후 응답 출력이 개시될 때까지의 시간은 응답시간이다

테스트 레벨
소프트웨어 테스트를 단계적으로 수행하는 V 모형의 4단계 (암기: 단통시인)
[구성] 단위 → 통합 → 시스템 → 인수
[의미] 작은 단위에서 시작해 전체로 확장하며 검증하는 구조
[구분] 단계별 의미
· 단위 테스트: 요구사항에 대한 단위 모듈, 서브루틴 테스트
· 통합 테스트: 단위 테스트를 통과한 모듈 사이의 인터페이스와 상호작용 검증
· 시스템 테스트: 전체 시스템에서 기능이 정상 동작하는지 검증
· 인수 테스트: 요구사항 만족 여부를 확인
[치트키] "단(단위) 통(통합) 시(시스템) 인(인수) = 단통시인"
[예문] 모듈 간 인터페이스를 검증하는 테스트 레벨은 통합 테스트이다

테스트 오라클
실제 결과와 비교할 기대 결과를 제공하는 기법 (암기: 참샘휴일)
[구성] 참 오라클 + 샘플링 오라클 + 휴리스틱 오라클 + 일관성 오라클
[의미] 테스트 결과의 정답 여부를 판단하는 기준 제공
[구분] 종류별 의미
· 참 오라클: 모든 입력값에 대해 기대하는 결과를 생성
· 샘플링 오라클: 일부 특정 입력값에 대해 기대 결과를 생성
· 휴리스틱(추정) 오라클: 특정 입력값에 대해 올바른 결과를 제공하고 나머지는 휴리스틱으로 처리
· 일관성 오라클: 수행 전과 수행 후의 결과값이 동일한지 확인
[치트키] "참(참) 샘(샘플링) 휴(휴리스틱) 일(일관성) = 참샘휴일"
[예문] 수행 전후의 결과값이 동일한지 확인하는 오라클은 일관성 오라클이다

기초 경로 검사(Basis Path Testing)
McCabe가 제안한 대표적인 화이트박스 테스트 기법
[구성] 제어 흐름 그래프 → 순환 복잡도 계산 → 독립 경로 도출
[의미] 모든 독립적인 경로를 한 번씩 실행하도록 테스트 케이스를 설계
[구분] 순환 복잡도 계산식
· V(G) = E - N + 2 (E: 간선 수, N: 노드 수)
· 폐구간(영역)의 개수에 1을 더해도 구할 수 있음
[치트키] "엣지에서 노드 빼고 2를 더한다 = E - N + 2"
[예문] 간선이 9개, 노드가 7개인 그래프의 순환 복잡도는 9 - 7 + 2 = 4이다

블랙박스 테스트 유형
내부 구조를 보지 않고 입출력 명세를 기준으로 수행하는 기능 테스트
[구성] 동등 분할 + 원인-효과 그래프 + 비교 검사 + 오류 예측 + 경계값 분석
[의미] 요구사항 명세를 기반으로 입력과 출력을 검증
[구분] 기법별 의미
· 동등 분할: 입력 자료를 동등한 그룹으로 나누어 대표값으로 테스트
· 원인-효과 그래프: 입력 데이터 간 관계와 출력에 영향을 미치는 상황을 분석해 효용성이 높은 케이스 선정
· 비교 검사: 동일한 테스트를 하여 동일한 결과가 출력되는지 확인
· 오류 예측: 과거 경험이나 테스터의 감각으로 테스트
· 경계값 분석: 입력 조건의 경계값을 테스트 케이스로 선정
· 페어 와이즈: 테스트 데이터의 최소한의 조합으로 적은 테스트 세트를 구성
[치트키] "동원인 비오면 경계한다 = 동등분할, 원인효과, 비교, 오류예측, 경계값"
[예문] 입력 조건의 최솟값과 최댓값 부근을 집중 테스트하는 기법은 경계값 분석이다

경계값 분석(Boundary Value Analysis)
입력 조건의 경계값을 테스트 케이스로 선정하는 블랙박스 테스트 기법
[구성] 최솟값 ±1 + 최댓값 ±1 + 경계값 자체
[의미] 오류가 경계 부근에서 자주 발생한다는 점에 착안
[치트키] "경계선 바로 앞뒤(±1)를 찔러 본다"
[예문] 입력 범위가 1~100일 때 0, 1, 100, 101을 테스트하는 기법은 경계값 분석이다
[헷갈리는 단어] 동등 분할 - 경계값은 경계 부근, 동등 분할은 그룹 대표값

테스트 드라이버(Driver)
상향식 테스트에서 테스트 대상 하위 모듈을 호출하고 파라미터를 전달하며 결과를 도출하는 도구
[구성] 가짜 상위 모듈 → 하위 모듈 호출
[의미] 아직 개발되지 않은 상위 모듈의 역할을 대신 수행
[치트키] "드라이버 = 운전자, 아래 모듈을 몰고 가는 가짜 상위 모듈"
[예문] 상향식 통합 테스트에서 상위 모듈을 대신하는 도구는 드라이버이다
[헷갈리는 단어] 스텁 - 드라이버는 상향식, 스텁은 하향식

스텁(Stub)
하향식 테스트에서 제어 모듈이 호출하는 타 모듈의 기능을 단순히 수행하는 도구
[구성] 가짜 하위 모듈 → 상위 모듈에서 호출
[의미] 아직 개발되지 않은 하위 모듈을 대신해 특정 값을 반환하거나 메시지를 출력
[치트키] "스텁 = 그루터기, 위에서 부르면 대충 대답하는 가짜 하위 모듈"
[예문] 하향식 통합 테스트에서 하위 모듈을 대신하는 도구는 스텁이다
[헷갈리는 단어] 드라이버 - 스텁은 하향식, 드라이버는 상향식

테스트 케이스
입력값, 실행조건, 기대 결과로 구성된 테스트 항목의 명세서
[구성] 입력값 + 실행 조건 + 기대 결과
[의미] 테스트를 재현 가능하게 하는 개별 항목 명세
[치트키] "넣고(입력) 조건대로 돌리고(실행조건) 이래야 한다(기대 결과)"
[예문] 입력값, 실행조건, 기대 결과로 구성된 명세서는 테스트 케이스이다
[헷갈리는 단어] 테스트 시나리오 - 케이스는 개별 항목, 시나리오는 케이스들의 집합

테스트 시나리오
테스트 수행을 위한 테스트 케이스들의 집합으로 케이스의 동작 순서를 기술한 문서
[구성] 테스트 케이스 여러 개 + 수행 순서
[의미] 업무 흐름 단위로 테스트 절차를 정리
[치트키] "시나리오 = 케이스들을 이어 붙인 이야기"
[예문] 여러 테스트 케이스의 동작 순서를 기술한 문서는 테스트 시나리오이다
[헷갈리는 단어] 테스트 케이스 - 시나리오는 케이스의 집합

테스트 커버리지
테스트를 얼마나 수행했는지 측정하는 기준
[구성] 명세 기반 + 구조 기반 + 경험 기반 / 기능 + 라인 + 코드 커버리지
[의미] 테스트의 충분성을 수치로 평가
[구분] 종류별 의미
· 명세 기반 테스트: 주어진 명세를 빠짐없이 테스트 케이스로 구현했는지 확인
· 구조 기반 테스트: 내부 논리 흐름에 따라 테스트 케이스를 작성하고 확인
· 경험 기반 테스트: 유사 소프트웨어와 기술 평가에서 테스터의 경험을 기반으로 수행
· 기능 기반 커버리지: 전체 기능을 모수로 수행된 기능 수를 측정
· 라인 커버리지: 전체 소스 코드 라인 수 대비 수행된 라인 수를 측정
· 코드 커버리지: 구문, 조건, 결정 등 코드 구조 자체가 얼마나 테스트되었는지 측정
[치트키] "무엇을 모수로 삼느냐 = 기능(기능), 줄(라인), 구조(코드)"
[예문] 전체 소스 코드의 라인 수 대비 수행된 라인 수를 측정하는 것은 라인 커버리지이다

코드 커버리지 구조
소스 코드의 구조를 기준으로 테스트 충분성을 측정하는 커버리지 종류 (암기: 변조조결구다경)
[구성] 변경 조건/결정 → 조건/결정 → 조건 → 결정 → 구문 → 다중 조건 → 경로
[의미] 어디까지 True와 False를 확인했는지에 따라 구분
[구분] 종류별 의미
· 변경 조건/결정 커버리지: 각 조건식이 결정 결과에 독립적으로 영향을 주도록 True/False를 확인
· 조건/결정 커버리지: 결정 포인트와 개별 조건식 둘 다 True/False를 가져야 함
· 조건 커버리지: 개별 조건식만 각각 True/False를 만족
· 결정 커버리지: 결정 포인트만 각각 True/False를 만족
· 구문 커버리지: 코드 내 구문이 한 번 이상 수행
· 다중 조건 커버리지: 결정 포인트 내 모든 개별 조건식의 가능한 조합을 100% 보장
· 경로 커버리지: 가능한 모든 경로를 수행
[치트키] "변조도 결국 다 걸린다 = 변조조결구다경"
[예문] 모든 조건식의 가능한 조합을 보장하는 커버리지는 다중 조건 커버리지이다

회복 테스트(Recovery)
시스템에 고의로 실패를 유도하고 정상적으로 복귀하는지 확인하는 테스트
[구성] 고의 장애 발생 → 복구 과정 → 정상 복귀 여부 확인
[의미] 장애 상황에서의 복구 능력 검증
[치트키] "회복 = 일부러 쓰러뜨려 놓고 일어나는지 본다"
[예문] 시스템에 고의로 실패를 유도해 정상 복귀 여부를 확인하는 테스트는 회복 테스트이다

스트레스 테스트(Stress)
임계점 이상의 부하를 계속 가해 비정상적인 상황에서의 처리를 확인하는 테스트
[구성] 임계점 초과 부하 → 시스템 한계와 장애 동작 관찰
[의미] 극한 상황에서 시스템이 어떻게 반응하는지 검증
[치트키] "스트레스 = 한계 이상으로 몰아붙인다"
[예문] 임계점 이상의 부하를 가해 비정상적인 상황에서의 동작을 보는 테스트는 스트레스 테스트이다
[헷갈리는 단어] 부하 테스트 - 스트레스는 임계점 이상, 부하는 임계점을 찾는 것

회귀 테스트(Regression)
오류 제거와 수정에 의해 새로 유입된 오류가 없는지 확인하는 일종의 반복 테스트
[구성] 수정 → 기존 테스트 재수행 → 신규 결함 여부 확인
[의미] 변경이 기존 기능에 악영향을 주지 않았음을 확인
[치트키] "회귀 = 고치고 나서 다시 돌아가 확인"
[예문] 코드 수정 후 이전에 통과한 기능이 여전히 동작하는지 재검증하는 테스트는 회귀 테스트이다

부하·내구성·스파이크 테스트
성능 관련 테스트 중 부하의 크기와 지속 시간, 순간 증가를 다루는 3가지 테스트
[구성] 부하(Load) + 내구성(Endurance) + 스파이크(Spike)
[의미] 시스템의 한계와 안정성을 다양한 부하 패턴으로 확인
[구분] 종류별 의미
· 부하: 시스템에 부하를 계속 증가시키며 임계점을 찾음
· 내구성: 오랜 시간 동안 시스템에 높은 부하를 가해 테스트
· 스파이크: 짧은 시간에 사용자가 몰릴 때 시스템의 반응을 측정
[치트키] "부하는 점점 올리고, 내구성은 오래 버티고, 스파이크는 순간 폭주"
[예문] 짧은 시간에 사용자가 몰릴 때의 반응을 측정하는 테스트는 스파이크 테스트이다

정적 분석 도구
코드를 실행하지 않고 소스 코드의 코딩 표준, 스타일, 복잡도, 남은 결함을 발견하는 도구
[구성] 소스 코드 분석 (비실행)
[의미] 코드 작성 단계에서 결함을 조기에 발견
[구분] 대표 도구
· PMD, SonarQube, Cppcheck, Checkstyle 등
[치트키] "정적 = 실행 없이 눈으로 코드만 검사"
[예문] 코드를 실행하지 않고 코딩 표준 위반과 복잡도를 검사하는 도구는 정적 분석 도구이다
[헷갈리는 단어] 동적 분석 도구 - 정적은 실행하지 않음, 동적은 실행하며 분석

동적 분석 도구
코드를 실행시켜 분석하고 디버깅으로 파일을 자세히 살펴보며 코드 흐름과 메모리 상태를 확인하는 도구
[구성] 프로그램 실행 + 실행 중 행위 분석
[의미] 실행 중에만 드러나는 결함과 메모리 문제를 발견
[치트키] "동적 = 돌려 보면서 관찰"
[예문] 프로그램을 실행하면서 코드 흐름과 메모리 상태를 확인하는 도구는 동적 분석 도구이다
[헷갈리는 단어] 정적 분석 도구 - 동적은 실행하며, 정적은 실행하지 않고 분석

LOC(Lines of Code) 기법
소프트웨어 규모를 코드 라인 수로 추정하는 상향식 비용 산정 방법
[구성] 낙관치 + 중간치 + 비관치를 1:4:1 가중치로 평균
[의미] 코드 라인 수의 낙관치, 중간치, 비관치를 측정하여 가중 평균으로 예측치를 구함
[구분] 관련 용어
· MM(Man Month): 한 사람이 한 달 동안 할 수 있는 일의 양
[치트키] "낙관 1, 중간 4, 비관 1 = 1:4:1"
[예문] 낙관치, 중간치, 비관치를 1:4:1로 가중하여 코드 라인 수를 추정하는 기법은 LOC 기법이다

COCOMO
프로그램 규모에 따라 조직형, 반분리형, 임베디드형으로 구분해 비용을 산정하는 수학적 방식
[구성] 조직형 + 반분리형 + 임베디드형
[의미] 소프트웨어 개발 규모(KDSI)에 기반해 노력과 기간을 예측
[구분] 유형별 규모
· 조직형: 5만 라인 이하
· 반분리형: 30만 라인 이하
· 임베디드형: 30만 라인 이상
[치트키] "5만 이하 조직, 30만 이하 반분리, 30만 이상 임베디드"
[예문] 소프트웨어를 조직형, 반분리형, 임베디드형으로 나누어 비용을 산정하는 모델은 COCOMO이다

형상 관리 절차
소프트웨어 개발 중 발생하는 모든 변경 사항을 관리하는 절차 (암기: 식통감기)
[구성] 4단계: 형상 식별 → 형상 통제 → 형상 감사 → 형상 기록
[의미] 산출물의 변경을 체계적으로 추적하고 통제
[구분] 단계별 의미
· 형상 식별: 관리 대상 항목을 선정하고 식별
· 형상 통제: 변경 요청이 있을 때 변경 여부와 변경 활동을 통제 (버전 관리)
· 형상 감사: 변경이 요구사항에 맞게 반영되었는지 검토
· 형상 기록: 변경 이력과 상태를 보고
· 베이스라인: 변화를 통제하는 시점의 기준
[치트키] "식(식별) 통(통제) 감(감사) 기(기록) = 식통감기"
[예문] 변경 요청이 있을 때 변경 여부와 활동을 통제하는 형상 관리 단계는 형상 통제이다

ODBC
데이터베이스에 접근하기 위한 표준 규격
[구성] 응용 프로그램 + ODBC 드라이버 + DBMS
[의미] DBMS 종류와 관계없이 같은 방식으로 데이터베이스에 접근하도록 하는 표준 인터페이스
[치트키] "ODBC = 어떤 DB든 통하는 공용 접속 규격"
[예문] DBMS 종류에 상관없이 표준 방식으로 DB에 접근하게 하는 규격은 ODBC이다
[헷갈리는 단어] JDBC - ODBC는 DB 접근 표준 규격, JDBC는 자바에서 DB에 접근하는 API

ORM
객체와 관계형 데이터베이스의 데이터를 자동으로 매핑(연결)해 주는 기술
[구성] 객체 + 관계형 DB 테이블 + 자동 매핑
[의미] SQL을 직접 작성하지 않고 객체 조작으로 DB를 다룰 수 있게 함
[치트키] "ORM = 객체(O)와 관계(R)를 이어 주는 매퍼(M)"
[예문] 객체와 관계형 데이터베이스의 데이터를 자동으로 매핑하는 기술은 ORM이다

직접 연계 방식 기술
송신 시스템과 수신 시스템 사이에서 중간 매개 없이 직접 데이터를 연계하는 주요 기술
[구성] DB Link + DB Connect + API/Open API + JDBC + Hyper Link
[의미] 시스템 간 데이터를 직접 연결해 주고받는 방식
[구분] 기술별 의미
· DB Link: 수신 시스템에서 DB 링크를 생성하고 송신 시스템에서 DB 링크를 직접 참조
· DB Connect: WAS에서 DB로 연결하는 DB 커넥션 풀을 생성하고 연계 프로그램이 커넥션 풀 이름으로 연결
· API/Open API: DB에서 데이터를 읽어서 제공하는 애플리케이션 프로그래밍 인터페이스
· JDBC: 수신 시스템 프로그램에서 JDBC 드라이버를 이용해 DB와 연결하는 자바 API
· Hyper Link: 현재 페이지에서 다른 부분이나 페이지로 이동
[치트키] "링크는 직접 링크, 커넥트는 풀, API는 읽어 주기, JDBC는 자바"
[예문] WAS에서 DB 커넥션 풀을 생성하여 DB에 연결하는 연계 방식은 DB Connect이다

미들웨어
양쪽을 연결하여 데이터를 주고받을 수 있도록 중간에서 매개 역할을 하는 소프트웨어
[구성] 클라이언트 ↔ 미들웨어 ↔ 서버
[의미] 서로 다른 시스템·플랫폼 간 통신을 쉽게 해 주는 소프트웨어 계층
[치트키] "미들웨어 = 중간에 끼어 연결해 주는 통역사"
[예문] 서로 다른 시스템 사이에서 데이터 교환을 중개하는 소프트웨어는 미들웨어이다

간트 차트
시간선 차트라고도 하며 작업이 언제 시작하고 종료되는지 일정을 막대 도표로 표시한 차트
[구성] 작업 + 기간(막대) + 일정
[의미] 프로젝트 일정 관리에 사용
[치트키] "간트 = 막대로 일정 보기"
[예문] 작업의 시작과 종료 일정을 막대 도표로 표시한 차트는 간트 차트이다
[헷갈리는 단어] PERT - 간트는 일정 막대 도표, PERT는 작업 상하관계 네트워크

PERT
프로젝트에 필요한 전체 작업의 상하관계를 표시한 네트워크
[구성] 작업 노드 + 선후 관계 화살표
[의미] 작업 간 선후 관계와 소요 시간을 분석하여 일정 관리에 활용
[치트키] "퍼트 = 작업을 줄줄이 이은 네트워크"
[예문] 전체 작업의 상하관계를 네트워크로 나타낸 일정 도구는 PERT이다
[헷갈리는 단어] 간트 차트 - PERT는 상하관계 네트워크, 간트는 막대 도표

APM(Application Performance Management)
전체 애플리케이션의 성능을 관리하기 위해 접속자, 트랜잭션, 장애 진단 등을 모니터링하는 도구
[구성] 접속자 모니터링 + 트랜잭션 모니터링 + 장애 진단
[의미] 애플리케이션 상태를 감시하고 성능 문제를 진단
[치트키] "APM = 애플리케이션 건강검진"
[예문] 애플리케이션 전체를 감시하고 성능을 관리하는 도구는 APM이다

인터페이스 구현 검증 도구
인터페이스가 정상 동작하는지 검증하는 테스트 도구 (암기: 엑스피 엔셀웨)
[구성] xUnit + STAF + FitNesse + NTAF + Selenium + Watir
[의미] 단위 테스트 프레임워크, 웹 테스트 도구 등으로 인터페이스 동작을 자동 검증
[구분] 도구별 의미
· xUnit: 다양한 언어를 지원하는 단위 테스트 프레임워크
· STAF: 서비스 호출, 컴포넌트 재사용 등 다양한 환경을 지원하는 테스트 프레임워크
· FitNesse: 웹 기반 테스트 케이스 설계·실행·결과를 지원, 테스트 케이스 테이블 작성 시 자동 테스트
· NTAF: STAF와 FitNesse의 장점을 통합한 네이버 개발 테스트 자동화 프레임워크
· Selenium: 다양한 브라우저와 개발 언어를 지원하는 웹 애플리케이션 테스트 프레임워크
· Watir: 루비를 사용하는 애플리케이션 테스트 프레임워크
[치트키] "엑스(xUnit) 스(STAF) 피(FitNesse) 엔(NTAF) 셀(Selenium) 웨(Watir)"
[예문] 다양한 브라우저를 지원하는 웹 애플리케이션 테스트 프레임워크는 Selenium이다

AJAX
웹 페이지 전체를 다시 로딩하지 않고도 일부분만 갱신할 수 있는 비동기 방식 처리 기술
[구성] 비동기 통신 + 부분 갱신
[의미] 사용자 경험을 높이는 웹 기술
[치트키] "AJAX = 새로고침 없이 일부만 쏙 바꾸기"
[예문] 페이지 전체를 새로 고치지 않고 일부만 비동기로 갱신하는 기술은 AJAX이다

JSON
키와 값의 쌍으로 이루어진 데이터 오브젝트를 전달하기 위한 XML을 대체하는 주요 데이터 포맷
[구성] 키 + 값 쌍
[의미] 가볍고 읽기 쉬워 웹 API에서 널리 사용
[치트키] "JSON = 키:값 짝으로 가볍게"
[예문] 키-값 쌍으로 데이터를 표현하며 XML을 대체하는 데이터 포맷은 JSON이다

XML
W3C에서 개발되었으며 호환 문제와 SGML의 복잡함을 해결하기 위해 개발된 다목적 마크업 언어
[구성] 태그 기반 + 사용자 정의 태그
[의미] 시스템 간 데이터 교환을 위한 표준 형식
[치트키] "XML = 태그를 내 마음대로 확장"
[예문] 호환 문제와 SGML의 복잡함을 해결하기 위해 개발된 다목적 마크업 언어는 XML이다

수학적 비용 산정 방법
수학적 공식을 이용해 개발 비용을 산정하는 하향식 방법
[구성] COCOMO + Putnam + FP
[의미] 규모나 기능에 기반한 모델로 비용을 계산
[구분] 모델별 의미
· COCOMO: 프로그램 규모에 따라 조직형, 반분리형, 임베디드형으로 구분
· Putnam: 시간과 노력의 Rayleigh-Norden 곡선을 기초로 단계별 필요 인력 분포를 계산
· FP(Function Point): 기능점수 모형
[치트키] "코코모는 규모 3유형, 푸트남은 레일리 곡선, FP는 기능점수"
[예문] Rayleigh-Norden 곡선을 기초로 인력 분포를 구하는 모델은 Putnam이다

베이스라인(Baseline)
개발 각 단계의 산출물을 검토·평가·조정하여 변화를 통제하는 시점의 기준
[구성] 정식 승인된 산출물 + 변경 통제 기준
[의미] 형상 관리에서 변경을 통제하는 대표적인 기준점
[치트키] "베이스라인 = 여기서부터는 함부로 못 바꾸는 기준선"
[예문] 형상 관리에서 변경 통제의 기준이 되는 승인된 산출물 시점은 베이스라인이다

미들웨어 유형
서로 다른 시스템 사이의 통신과 데이터 교환을 중개하는 미들웨어의 종류
[구성] DB + RPC + MOM + TP-Monitor + ORB + WAS
[의미] 중개 방식에 따라 구분
[구분] 유형별 의미
· DB: 데이터베이스 접근을 중개
· RPC: 원격 프로시저 호출
· MOM: 메시지 지향 미들웨어, 메시지 큐 기반
· TP-Monitor: 트랜잭션 처리를 감시하고 관리
· ORB: 객체 요청 브로커, 분산 객체 간 통신
· WAS: 웹 애플리케이션 서버
[치트키] "DB·RPC·MOM·TP·ORB·WAS = 6가지"
[예문] 메시지 큐를 이용해 비동기 메시지를 전달하는 미들웨어는 MOM이다

화이트박스 테스트
프로그램 내부 구조와 논리 경로를 보고 수행하는 구조 기반 테스트
[구성] 기초 경로 테스트 + 제어 흐름 커버리지 + 루프 테스트 + 데이터 흐름 테스트
[의미] 내부 로직을 알고 모든 경로와 조건을 확인
[구분] 커버리지 종류
· 구문 커버리지: 모든 문장을 1회 이상 실행
· 결정 커버리지: 모든 분기의 참과 거짓을 1회 이상
· 조건 커버리지: 각 조건식의 참과 거짓
· 조건-결정 커버리지: 조건과 결정 모두
· 다중 조건 커버리지: 모든 조건 조합
[치트키] "화이트박스 = 속이 훤히 보이는 상자"
[예문] 내부 로직과 경로를 보며 수행하는 테스트는 화이트박스 테스트이다
[헷갈리는 단어] 블랙박스 테스트 - 화이트박스는 내부 구조, 블랙박스는 입출력 명세

검증(Verification)과 확인(Validation)
소프트웨어 품질을 확인하는 두 가지 관점
[구성] 검증: 제품을 올바르게 만들고 있는가 + 확인: 올바른 제품을 만들었는가
[의미] 개발 과정과 결과물을 서로 다른 관점에서 점검
[구분] 관점별 차이
· 검증: 개발자 관점, 과정 중심
· 확인: 사용자 관점, 결과 중심
[치트키] "검증은 만드는 과정, 확인은 만든 결과"
[예문] 사용자 관점에서 올바른 제품을 만들었는지 점검하는 활동은 확인이다

형상 관리 도구
소프트웨어 변경 이력과 버전을 관리하는 도구
[구성] Git + SVN + CVS
[의미] 협업 개발 시 변경 사항을 추적하고 충돌을 해결
[구분] 도구와 용어
· Git: 분산형 버전 관리
· SVN: 중앙집중형
· CVS: 초기 중앙집중형 도구
· 용어: 커밋, 체크아웃, 체크인, 브랜치, 머지, 충돌
[치트키] "Git은 분산, SVN은 중앙"
[예문] 분산형 버전 관리 도구는 Git이다

릴리즈 노트
고객에게 개발 과정에서 정리된 상세 서비스 정보와 제품 수정·변경·개선 내용을 제공하는 문서
[구성] 헤더 + 개요 + 목적 + 이슈 요약 + 재현 항목 + 수정·개선 내용 + 사용자 영향도 + SW 지원 영향도 + 노트 + 면책 조항 + 연락 정보
[의미] 소프트웨어 제품과 함께 배포되는 문서로 배포 버전의 변경 사항을 사용자에게 알림
[구분] 주요 작성 항목
· 헤더: 문서 이름, 제품 이름, 버전 번호, 릴리즈 날짜, 참고 날짜, 노트 버전 등
· 개요: 제품 및 변경에 대한 간략한 전반적 개요
· 목적: 릴리즈 버전의 새로운 기능 목록과 노트의 목적, 버그 수정 및 새 기능
· 이슈 요약: 버그의 간단한 설명 또는 릴리즈 추가 항목 요약
· 재현 항목: 버그 발견에 따른 재현 단계
· 수정·개선 내용: 수정·개선의 간단한 설명
· 사용자 영향도: 최종 사용자 기준 기능·응용 프로그램상의 영향도
· 소프트웨어 지원 영향도: 소프트웨어의 지원 프로세스 및 영향도
· 노트: 소프트웨어·하드웨어 설치 항목, 제품 문서를 포함한 업그레이드 항목 메모
· 면책 조항: 회사 및 표준 제품과 관련된 메시지, 불법 복제 방지 등 고지 사항
· 연락 정보: 사용자 지원 및 문의 연락처
[치트키] "머리(헤더)에서 시작해 개요·목적 → 이슈·재현 → 수정 → 영향도 → 노트·면책·연락"
[예문] 릴리즈 노트에서 문서 이름, 제품 이름, 버전 번호, 릴리즈 날짜가 들어가는 항목은 헤더이다

리팩토링(Refactoring)의 목적
소프트웨어의 외부 기능은 바꾸지 않고 내부 구조와 관계를 단순화하여 유지보수성을 높이는 기법
[구성] 유지보수성 향상 + 유연한 시스템 + 생산성 향상 + 품질 향상
[의미] 중복 제거와 단순화로 코드를 개선하는 XP의 핵심 원리
[구분] 목적별 의미
· 유지보수성 향상: 복잡한 코드를 단순화하고 가독성 향상
· 유연한 시스템: 요구사항 변경에 유연하게 대응
· 생산성 향상: 정제·최적화된 소스를 재사용
· 품질 향상: 오류 발견이 쉬워져 품질이 좋아짐
[치트키] "유(유지보수) 유(유연) 생(생산성) 품(품질)"
[예문] 기능은 그대로 두고 내부 구조를 개선해 유지보수성을 높이는 기법은 리팩토링이다

통합 테스트 방식
단위 테스트를 마친 모듈을 결합하며 인터페이스를 검증하는 방식
[구성] 빅뱅 + 하향식 + 상향식 + 샌드위치(혼합식)
[의미] 모듈을 한꺼번에 결합할지, 위에서/아래에서 단계적으로 결합할지에 따라 구분
[구분] 방식별 특징
· 빅뱅: 모든 모듈을 한 번에 결합 (소규모에 적합)
· 하향식: 상위에서 하위로 진행하며 하위 모듈 대신 스텁(Stub) 사용
· 상향식: 하위에서 상위로 진행하며 상위 모듈 대신 드라이버(Driver) 사용
· 샌드위치: 하향식과 상향식을 병행
[치트키] "스텁은 하향식(가짜 하위), 드라이버는 상향식(가짜 상위)"
[예문] 하향식 통합 테스트에서 하위 모듈을 대신하는 더미 모듈은 스텁이다
[헷갈리는 단어] 스텁과 드라이버 - 2026년 1회에서도 하위 대체는 스텁, 상위 대체는 드라이버로 출제

알파 테스트와 베타 테스트
인수 테스트의 두 가지 방식
[구성] 알파 테스트 + 베타 테스트
[의미] 사용자가 실제로 사용해 보며 요구사항 만족 여부를 확인하는 테스트
[구분] 차이
· 알파: 선택된 사용자가 개발자 환경에서 통제된 상태로 개발자와 함께 수행
· 베타: 실제 환경에서 일정 수의 사용자가 사용하고 피드백을 제공
[치트키] "알파는 개발자 집, 베타는 사용자 집"
[예문] 실제 사용자 환경에서 일부 사용자에게 사용하게 하고 피드백을 받는 인수 테스트는 베타 테스트이다

CASE 도구
소프트웨어 개발 과정을 자동화하여 생산성과 품질을 높이는 도구
[구성] 상위(Upper) CASE + 하위(Lower) CASE
[의미] 분석·설계 단계 도구와 구현·테스트 단계 도구로 구분
[구분] 유형
· 상위 CASE: 요구사항 분석과 설계 지원
· 하위 CASE: 코드 작성, 테스트, 문서화 지원
[치트키] "상류는 설계, 하류는 코딩"
[예문] 요구사항 분석과 설계 단계를 지원하는 CASE 도구는 상위 CASE이다

HIPO 차트
입력, 처리, 출력의 관점에서 시스템을 계층적으로 표현하는 문서화 도구
[구성] 가시적(도식) 도표 + 총체적(개요) 도표 + 세부적 도표
[의미] 시스템의 기능을 입력-처리-출력으로 나누어 시각화
[치트키] "HIPO = 입력(I) 처리(P) 출력(O) 계층도"
[예문] 입력, 처리, 출력을 중심으로 시스템 기능을 계층적으로 도식화하는 도구는 HIPO 차트이다

배드코드(Bad Code) 사례
가독성과 유지보수성을 떨어뜨리는 나쁜 코드의 유형
[구성] 외계인 코드 + 스파게티 코드 + 알 수 없는 변수명 + 로직 중복
[의미] 리팩토링과 클린코드로 개선해야 할 코드 냄새
[구분] 사례별 의미
· 외계인 코드: 작성자가 아닌 사람이 이해하기 어려운 코드
· 스파게티 코드: 제어 흐름이 얽힌 복잡한 코드
· 알 수 없는 변수명: 의미를 파악할 수 없는 이름
· 로직 중복: 같은 로직이 여러 곳에 반복
[치트키] "스파게티 면발처럼 얽힌 코드"
[예문] 제어 흐름이 복잡하게 얽혀 읽기 어려운 코드를 스파게티 코드라 한다

CMMI 성숙도 단계
소프트웨어 개발 조직의 프로세스 성숙도를 평가하는 모델의 단계적 표현 5단계
[구성] 초기화(초기) → 관리 → 정의 → 정량적 관리 → 최적화
[의미] 프로세스가 체계화될수록 높은 단계로 평가
[구분] 단계별 의미
· 초기화: 프로세스가 비정형적이고 개인 역량에 의존
· 관리: 프로젝트 단위로 계획과 관리
· 정의: 조직 표준 프로세스를 정의
· 정량적 관리: 수치로 프로세스를 측정·통제
· 최적화: 지속적으로 프로세스를 개선
[치트키] "초 관 정 정량 최 = 처음엔 관리, 정의하고 수치로 재고 최적화"
[예문] 프로세스를 정량적으로 측정하고 통제하는 CMMI 단계는 정량적 관리 단계이다

소프트웨어 공학 원칙 관련 법칙
소프트웨어 공학에서 자주 인용되는 3가지 법칙
[구성] 브룩스의 법칙 + 파레토 법칙 + 롱테일 법칙
[의미] 인력 투입, 결함 분포, 소수 vs 다수에 관한 경험 법칙
[구분] 법칙별 의미
· 브룩스의 법칙: 지연된 프로젝트에 인력을 추가하면 오히려 더 늦어짐
· 파레토 법칙: 전체 결함의 80%는 전체 모듈의 20%에서 발생
· 롱테일 법칙: 소수의 인기 항목보다 다수의 비인기 항목이 모여 큰 가치를 이룸
[치트키] "브룩스 = 사람 늘려도 늦어진다, 파레토 = 8대2, 롱테일 = 긴 꼬리"
[예문] 지연된 프로젝트에 인력을 추가하면 더 지연된다는 법칙은 브룩스의 법칙이다

배치 프로그램 유형
사용자 개입 없이 일괄적으로 처리되는 배치 프로그램의 실행 유형
[구성] 이벤트 배치 + 온디맨드 배치 + 정기 배치
[의미] 실행 시점의 트리거에 따라 구분
[구분] 유형별 의미
· 이벤트 배치: 특정 이벤트가 발생하면 실행
· 온디맨드 배치: 사용자의 요청이 있을 때 실행
· 정기 배치: 정해진 주기(일, 주, 월)에 따라 실행
[치트키] "이벤트는 사건, 온디맨드는 요청, 정기는 시간표"
[예문] 매일 밤 12시에 실행되는 배치 프로그램은 정기 배치이다

BCP(비즈니스 연속성 계획)
각종 재해나 재난에 대비하여 핵심 업무 기능의 연속성을 유지하기 위한 계획과 절차
[구성] BIA + RTO + RPO + DRP + DRS
[의미] 고객 서비스의 지속성과 신뢰도를 보장하는 체계
[구분] 주요 용어
· BIA: 장애·재해로 인한 손실을 가정해 시간 흐름에 따른 영향도와 손실을 평가하고 복구 우선순위를 도출
· RTO: 업무 중단 시점부터 복구되어 다시 가동될 때까지의 목표 시간
· RPO: 데이터 손실을 허용할 수 있는 목표 시점
· DRP: 장기간 시설 운영이 불가능한 재난에 대비한 복구 계획
· DRS: 복구 계획을 지원하기 위해 평소 확보하는 인적·물적 자원과 관리 체계가 통합된 재해복구센터
[치트키] "BIA로 영향 분석 → RTO·RPO로 목표 → DRP로 계획 → DRS로 시설"
[예문] 재해복구 시 데이터 손실을 허용할 수 있는 시점을 정한 목표는 RPO이다

DRP(재해 복구 계획)
재난으로 장기간에 걸쳐 시설의 운영이 불가능한 경우를 대비한 재난 복구 계획
[구성] 재난 평가 + 복구 절차 + 복구 자원
[의미] BCP의 하위 계획으로 복구 전략과 절차를 문서화
[치트키] "DRP = 재난 복구 계획서(Plan), DRS = 복구 센터(System)"
[예문] 재난 발생 시 복구 절차를 정의한 계획은 DRP이다
[헷갈리는 단어] DRS - DRP는 계획, DRS는 이를 지원하는 복구센터(시스템)

BIA(비즈니스 영향 분석)
재해 발생 시 기업의 비즈니스에 영향을 미치는 업무를 선정하고 업무 중단 영향을 분석하여 복구 우선순위를 도출하는 활동
[구성] 핵심 업무 선정 + 중단 영향 분석 + 복구 우선순위 도출
[의미] BCP 구축의 첫 단계로 손실 평가를 수행
[치트키] "BIA = 비즈니스(B) 영향(I) 분석(A)"
[예문] 업무 중단 시 영향을 분석해 복구 우선순위를 정하는 활동은 BIA이다
