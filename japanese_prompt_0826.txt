=== 프롬프트 평가 (2026-08-26) ===
평가 대상: prompt japanese.txt (현재 사용 중인 최신 버전)
평가 기준: app.py 실제 코드 (파싱 로직 / 렌더링 로직 / 학습·연습·시험 흐름 / 한자 풀이 사전)

--------------------------------------------------------------
1. 총평
--------------------------------------------------------------
형식(파싱 안전 규칙) 측면에서는 app.py 코드와 한 줄 한 줄 정확히 맞물리는, 매우 잘 만들어진 프롬프트입니다.
반면, "한자 암기"라는 목적에 비추어 보면 프롬프트가 만들어내는 방대한 분량의 한자 풀이가
app.py의 실제 학습 루프에서는 전부 "선택적 힌트"로만 쓰이고, 정답을 맞히는 채점/반복 로직과는
전혀 연결되어 있지 않다는 구조적 한계가 있습니다. 즉 "잘 쓰여진 참고서"는 만들어지지만,
듀오링고처럼 "한자를 능동적으로 떠올리고 즉시 피드백받는" 루프는 지금 이 프롬프트만으로는 만들어지지 않습니다.

--------------------------------------------------------------
2. 강점 — 코드와 정확히 맞물리는 규칙들
--------------------------------------------------------------
· 콜론 금지 (규칙 3): app.py의 parse_word_text()는 블록의 1번째 줄에 ":"가 있으면
  무조건 "단어:뜻" 한 줄 형식으로 오인식합니다 (if ":" in block[0]: ...).
  프롬프트가 1번째 줄에 콜론을 절대 못 쓰게 막은 것은 장식이 아니라 실제 파싱 버그를 막는 필수 규칙입니다.

· 빈 줄 규칙 (규칙 1, 2): parse_word_text()는 공백 줄을 기준으로 블록을 나누므로,
  "항목 내부 빈 줄 금지 / 항목 사이 빈 줄 정확히 1개"는 파서 동작과 100% 일치합니다.

· 부등호(<, >) 금지 (규칙 6): app.py는 힌트를 st.markdown(..., unsafe_allow_html=True)로
  그대로 HTML에 꽂아 넣습니다 (card_html += f"...{{cw['hint'].replace(chr(10), '<br>')}}..."`).
  힌트 안에 <, >가 들어가면 진짜로 HTML 태그로 해석되어 화면이 깨집니다. 근거가 명확한 규칙입니다.

· 마크다운 금지 (규칙 7): 같은 이유로 unsafe_allow_html 컨텍스트에서는 마크다운 렌더링이
  일관되지 않게 동작할 수 있어, ★·【】 같은 순수 유니코드 기호만 쓰라는 지침은 안전한 선택입니다.

· "반복 금지 규칙"(같은 한자라도 매번 새로 설명): 앱은 연습 모드에서 requeue_position()으로
  단어를 무작위 순서로 재노출시키므로, 같은 한자가 다른 단어에서 다시 나올 때마다 표현을 살짝 바꿔주는
  것은 사용자가 매번 새로운 각도로 복습하게 되어 스페이싱 효과(spacing effect) 관점에서 합리적입니다.

--------------------------------------------------------------
3. 구조적 약점 / 리스크
--------------------------------------------------------------
① 힌트는 "능동 회상"과 분리되어 있음
  study/practice/exam 세 모드 모두 채점 대상은 word ↔ meaning(뜻+독음) 한 쌍뿐입니다.
  practice_active()의 apply_score(100/60/40/0)도, exam의 정답/오답 판정도 모두 "단어 전체를 맞혔는가"만
  봅니다. 프롬프트가 그렇게 공들여 만드는 [읽기]/음독·훈독/분해/어원 같은 필드는 "힌트 보기" 버튼을
  눌러야만 노출되는 부가 텍스트일 뿐, 그 자체가 퀴즈로 출제되거나 채점되지 않습니다.
  → 결과적으로 "한자를 몇 번이나 봤는가"는 늘지만, "그 한자를 능동적으로 인출했는가"는 측정되지 않습니다.
  → 진짜 "한자 암기용 프롬프트"를 원한다면, 프롬프트의 내용 자체보다 이 내용을 앱이 어떻게
    소비하는지(퀴즈화하는지)가 더 중요한 병목입니다.

② 한자 풀이 사전(RADICAL_LIBRARY)과의 중복 가능성
  app.py는 정답 확인 후 render_char_breakdown(word)를 호출해, 강희자전 214개 부수 중
  단어에 포함된 글자가 있으면 자동으로 "한자 풀이" expander를 별도로 띄웁니다 (resources/radicals.json).
  예를 들어 木·水·火·金·土·人·女·子·心처럼 그 자체가 부수인 한자가 단어에 단독으로 쓰이면,
  프롬프트가 힌트에 적어 넣은 [한자1] 분해/어원 설명과 앱이 자동으로 붙이는 부수 설명이 화면에
  이중으로 뜹니다. 서로 다른 문체/깊이로 같은 내용이 두 번 나오는 셈이라 다소 산만할 수 있습니다.
  (참고: 이 자동사전은 214개 "부수"만 알고 있고, 機·能처럼 부수가 아닌 복합 한자는 인식하지 못하므로
  겹치는 사례 자체는 많지 않습니다만, 기초 단어일수록 겹칠 확률이 올라갑니다.)

③ 힌트 길이와 카드 UI
  .hint-box에는 max-height/스크롤 제한이 없습니다. 프롬프트 템플릿대로면 한자 2개짜리 단어도
  최소 15~20줄이 나오는데, 이게 그대로 카드 안에 펼쳐지면 모바일에서 스크롤이 매우 길어집니다.
  듀오링고 특유의 "짧게 보고 바로 다음"이라는 리듬과는 다소 배치되는 분량입니다.
  (수집형 참고서로는 훌륭하지만, "빠른 카드 넘김" 경험과는 트레이드오프가 있습니다.)

④ 대량 생성 시 품질 편차 리스크 (프롬프트 자체보다는 운용 문제)
  방금 51-60 배치(235단어)를 5개로 쪼개 병렬 생성해봤을 때도, 자간·표현 스타일이 청크마다
  미묘하게 다릅니다(예: 장음 표기 "-" 사용 빈도, 치트키 말투 등). 프롬프트에 "같은 배치 안에서는
  문체를 통일하라"는 명시적 지침이 없어서, 실제로 여러 번 나눠 돌리면 문체가 흔들릴 수 있습니다.

⑤ 읽기(독음)가 별도 필드로 분리되어 있지 않음
  2번째 줄 형식이 "뜻(읽기)" 한 문자열로 합쳐져 있어서, app.py 입장에서는 이것이 통째로 meaning
  값입니다. 나중에 "독음만 보고 뜻 맞히기" 같은 세분화된 퀴즈 모드를 만들고 싶어져도, 지금 데이터
  구조로는 독음만 따로 뽑아낼 수 없습니다(정규식으로 괄호를 파싱해야 함).

--------------------------------------------------------------
4. 개선 아이디어 (참고용 — 아직 실행하지 않았습니다)
--------------------------------------------------------------
· 힌트를 "핵심 요약 1~2줄 + 상세 접기"로 나누는 구조를 고려해볼 만합니다(단, app.py 쪽 렌더링도
  같이 손봐야 함 — 프롬프트만 바꿔서는 카드 길이 문제가 해결되지 않습니다).
· RADICAL_LIBRARY를 214개 부수에서 실제 학습 중인 한자 전체로 확장하고, "부수만 모아서 학습"처럼
  "한자만 모아서 학습/연습" 모드를 만들면, 프롬프트가 만드는 [한자1]/[한자2] 데이터를 능동 회상
  퀴즈로 직접 재활용할 수 있습니다 (지금은 텍스트로만 소비되고 버려지는 데이터입니다).
· 같은 배치 내 문체 통일을 위해 "이 배치에서 이미 나온 치트키 말투/장음 표기 규칙을 유지하라" 같은
  일관성 지침을 프롬프트에 추가하는 것을 고려해볼 수 있습니다.
· "뜻(읽기)" 대신 별도 줄로 읽기를 분리하는 포맷 변경은, app.py의 parse_word_text /
  build_word_pool / 오답노트 키 로직까지 함께 바꿔야 하는 큰 변경이라 신중히 판단해야 합니다.

5. 결론
--------------------------------------------------------------
형식 규칙은 그대로 유지할 가치가 충분합니다 — 전부 실제 코드에 근거가 있습니다.
다만 "한자 암기"라는 목적을 더 강하게 달성하려면, 프롬프트 문구를 다듬는 것보다
app.py 쪽에 "한자 자체를 능동적으로 테스트하는 루프"를 추가하는 쪽이 우선순위가 높아 보입니다.
프롬프트는 좋은 재료를 만들고 있지만, 지금 앱은 그 재료를 "읽고 넘어가는 부교재"로만 쓰고 있습니다.
